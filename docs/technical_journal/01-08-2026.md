# 01-08-2026

Ran `log_viz` for the first time and read it end to end. Detoured into what the session logs would look like as traces rather than logs. Then ported steps 6 and 7 Ruby → Python.

## Running log_viz

- `bundle install` then `bundle exec ruby bin/log_viz`, serving on <http://localhost:4567>. Deps are `sinatra`, `rackup`, `puma` — the only place in `week1_baseline/ruby/` that takes third-party gems, which the no-library rule in `ITERATIONS.md` covers because it's a viewer, not the agent.
- Reads `.boukensha/sessions/*.jsonl` and writes nothing back. Sessions dir overridable via `LOG_VIZ_SESSIONS_DIR`, plus `PORT` / `BIND`.
- **First run showed "No session logs found in `week1_baseline/.boukensha/sessions`" — an off-by-one in the default path.** `app.rb` expanded `../../../../.boukensha/sessions` from `lib/log_viz`, which is four levels up to `week1_baseline/`; the repo root is five. The README already claimed `<repo root>`, so the docs were right and the code was wrong.
- Fixed by anchoring to **`BOUKENSHA_DIR` when set**, falling back to five-up. That's the actual source of truth — `examples/example.rb` line 1 in every step does `ENV["BOUKENSHA_DIR"] ||= File.expand_path("../../../../.boukensha", __dir__)`, which is why logs land at the repo root rather than the `~/.boukensha` that `Config::DEFAULT_DIR` specifies. Precedence is now `LOG_VIZ_SESSIONS_DIR` → `$BOUKENSHA_DIR/sessions` → repo root; all three verified.
- **Lesson: the viewer hardcoded a path the agent derives from an env var.** Any hardcoded second copy of a configurable path is a drift waiting to happen — the fix was to read the same variable rather than to count `..` more carefully.
- Two routes: `/` lists sessions (start, id, task, model(s), iterations, in/out tokens, peak ctx %, cost); `/sessions/:id` renders one as a chat transcript with a stats strip on top.

## What's actually in there

- `lib/log_viz/session.rb` — the parser. Streams the JSONL and folds `session_start` / `turn` / `iteration` / `prompt` / `response` / `tool_call` / `tool_result` / `turn_end` / `compaction` / `reasoning` / `plan` into an ordered `Entry` list.
- **`response` events are the source of truth for task/provider/model/cost**, not `session_start` — which is what lets one session mix models and still attribute each call correctly.
- `MODEL_PRICES` in `session.rb` is a *fallback only*: `point_cost` prefers the logger's own `cost_usd` and only falls back to the local per-MTok table for older logs. Unknown model → `nil` → renders `—` rather than a wrong number.
- `lib/log_viz/ansi.rb` converts ANSI SGR codes in tool results to `<span>`s, so raw MUD output keeps its colours.
- Sparkline and budget bars are hand-rolled inline SVG/CSS — no JS, no chart library, consistent with the rest of the week.

## Step-06 logs only exercise part of the viewer

- **`06_the_logger`'s `example.rb` calls `Boukensha::Logger.new` with no `snapshot`**, so `session_start` carries only `phase` / `session_id` / `at`.
- The snapshot is where every denominator lives — `max_iterations`, `max_turn_tokens`, `context_window`, `model`, `provider`. It arrives in two instalments: the step-07 `.run` DSL adds `task` / `max_iterations` / `max_output_tokens` / `model` / `provider`, and `max_turn_tokens` / `context_window` wait until `12_context/lib/boukensha.rb:93`.
- Consequence: viewing a step-06 log, all three progress bars (peak context, largest turn, iterations) are skipped by their `> 0` guards and the stats strip degrades to the session-total line. Cost breakdown and the transcript still render, because those come from `response` events.
- Same shape for `compaction` / `reasoning` / `plan` entries — the templates handle them, but nothing emits them until later steps. **The viewer was written against step-12-era logs.**
- Not a bug, but worth knowing before concluding the bars are broken.

## Findings to fix later

- **`log_viz/README.md` has drifted behind the code** — its "What it does" lists neither the budget bars, the sparkline, the turn strips, nor the reasoning/plan/compaction entries. Third README drift this week (see 28-07, 31-07); the pattern is now consistent enough to expect rather than discover.
- **`pending_calls.shift` pairs tool calls to results positionally**, not by id. A `tool_call` with no matching `tool_result` silently shifts every later pair onto the wrong call. Hasn't bitten yet because the loop always emits both.

## Observability: logs yes, traces no

- Grepped the whole repo for `opentelemetry|otel|span|trace_id|jaeger|zipkin|tempo|honeycomb`. **Zero real hits** — every match was an HTML `<span>` in `ansi.rb` / `app.rb`. There is no tracing anywhere.
- **But the log format is already span-shaped.** `session_start` → `iteration` → paired `prompt`/`response` and `tool_call`/`tool_result`, each stamped `at`, closed by `turn_end`. `session.rb` reconstructs that tree in memory — the `pending_calls` pairing *is* span correlation, done positionally instead of by id.
- Missing to make them real traces: span id, parent span id, duration (derivable by subtracting the paired `at`s, never recorded), and status on the LLM calls. Attributes are already rich — `provider`, `model`, `task`, `usage`, `cost_usd`, `usage_unit`.
- **The stdlib-first rule points away from the `opentelemetry-sdk` gem** and toward emitting OTLP JSON over `net/http` — the same "hit the REST API directly" choice already made for the model providers. OTLP is `POST /v1/traces` with a `resourceSpans` payload.
- Cheapest first step, worth doing on its own merits: add `span_id` / `parent_span_id` to `Logger#write_log`. Backwards compatible (log_viz ignores unknown keys) and it retires the fragile `shift` pairing above.

## Hypothetical: the same agent on GCP Agent Engine

Not something being built — asked to understand how the managed path differs.

- **Trace Explorer is read-only.** Nothing is manipulated there; every attribute has to be attached in-process before the span is exported. Trace Explorer's role is that span attributes become the filter/group/chart dimensions.
- Agent Engine / ADK auto-instruments via OpenTelemetry into Cloud Trace: spans named `invoke_agent`, `call_llm`, `execute_tool`, `generate_content`, carrying `gen_ai.agent.name`, `gcp.vertex.agent.invocation_id`, `gcp.vertex.agent.event_id`. Enabled by `GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true` (newer) or `enable_tracing=True` on the constructor (older examples).
- Two ways to add to a tree you didn't create:
  - **Decorate the active span** — `trace.get_current_span().set_attribute(...)` inside a tool. ADK's span is current, so it just works. For facts *about* an existing step; adds no rows to the waterfall.
  - **Open a child span** — `tracer.start_as_current_span("validate_order")`. For work with real duration worth isolating. Nests automatically via context propagation.
- **Naming:** use `gen_ai.*` semconv where one exists (that's what makes the built-in dashboards light up), own prefix for everything else. Never a bare `region` or `cost` — unprefixed keys collide with platform-reserved ones. `gen_ai.*` was still experimental and churning; pin to a spec version actually read.
- Three gotchas: **attribute limits** (capped per span, long values truncated — a full prompt body will not survive as an attribute; put it in logs correlated by trace id); **sampling** (an attribute set is not guaranteed present on any given request, so billing/audit data must not live only on a span); **cardinality** (a session id is fine to filter one trace by, expensive as a chart grouping).
- **Takeaway:** `task` / `provider` / `model` / `cost_usd` are already exactly what "custom span attributes" means on a managed platform. The plumbing is what Agent Engine takes over; the judgment about which facts are worth attaching is the part that transfers — and sampling is why the JSONL logger wouldn't be redundant even on a fully-traced platform.

Sources: [Trace an agent](https://docs.cloud.google.com/agent-builder/agent-engine/manage/tracing), [Instrument ADK applications with OpenTelemetry](https://docs.cloud.google.com/stackdriver/docs/instrumentation/ai-agent-adk), [Cloud Trace observability for ADK](https://adk.dev/integrations/cloud-trace/), [ADK Traces](https://adk.dev/observability/traces/), [Gemini Enterprise Agent Platform tracing](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/tracing).

## Step 6 (The Logger)

- **Delta again far larger than "a `logger.rb` being added."** `agent.rb` substantially rewritten, `boukensha.rb` gains module state (`config` / `quiet!` / `debug!`), and `config.rb` / `errors.rb` each *delete* something. Three more files show in `diff` but need no Python change: `context.rb` is whitespace, `config.rb`'s first hunk is alignment, and `prompt_builder.rb`'s `attr_reader :backend` is already a public attribute in Python.
- **This step changed what "output" means.** Every `puts` left `agent.rb`; the artifact is now the `.jsonl`. Stdout shrank to an 8-line header plus the final response — so the prefix diff got *stronger* while covering less of what matters. Verification was rebuilt around a structural diff of the two session files: phase sequence, key list, and **key order** per event, with volatile fields normalised. 10 events each, identical.
- **`runtime.py` exists only in Python.** Ruby's `Boukensha.config` resolves at call time, so module state in `lib/boukensha.rb` is fine. The literal transcription — state in `__init__.py` — is a circular import, since `__init__` imports `logger` and `logger` would import `__init__`. A separate module avoids the cycle without a deferred-import trick; everything is re-exported so callers still write `boukensha.config()`.
- **First step to hit Ruby's `!`/`?` suffixes**, so it set the convention for the rest of the port: `set_quiet()` / `set_loud()` / `is_quiet()` / `set_debug()` / `is_debug()`. A bare `quiet()` would be ambiguous between setter and getter.
- **`ensure_ascii=False` turned out to be load-bearing.** Ruby's `JSON.generate` emits raw UTF-8. The agent logs `"(tool use — N calls)"` with an em dash, which default `json.dumps` escapes to `—`. `separators=(",", ":")` was already known from step 05; this one was new and would only ever have shown up as a byte diff.
- **`Time#iso8601` has no fractional seconds.** Python's `isoformat()` defaults to microseconds. Needed `timespec="seconds"` — confirmed against the real logs before writing the code, not after.
- **`.compact` is selective, so a blanket None-strip would be wrong.** Only the `response` event's task/provider/model/cost block drops nils. `tool_result` deliberately keeps `"error":null`, `turn_end` keeps `"tokens":null`.
- **`task.task_name` needs parentheses in Python** — it's a `classmethod`, so `hasattr` passes and the literal transcription hands `json.dumps` a bound method, raising `TypeError` on the very first `response` event. Predicted in the plan, so it never actually fired.
- **`logger=Logger()` as a default argument would share one file handle across every Agent** — Python evaluates defaults once at def-time. Same reasoning for `snapshot={}`.
- **`LoopError` deleted one step after step 05's plan recommended porting it** "for surface parity". Noted at the time that surface parity is a per-step decision, not a standing one. Step 7 made that point again, harder.
- Verified: prefix diff identical; JSONL structural diff clean; 29 offline logger checks; 25 offline loop-integration checks; both live runs exit 0 and parse in `log_viz`.

## Step 7 (The Run DSL)

- **`run_dsl.rb` is 13 lines and is not the step.** The step is the ~80-line `Boukensha.run` added to `lib/boukensha.rb`, which collapses the example from 92 lines to 34. `RunDSL#tool` is a pure passthrough to `Registry#tool` — it adds no behaviour.
- **What the block is actually for:** `run` must build the `Registry` itself (it attaches to the `Context` that `run` also builds), but the caller knows which tools they want, and they must be registered *before* the PromptBuilder serialises them. The block is the handoff at that one moment. `instance_eval` is a separate concern — it rebinds `self` so tools read as a bare `tool "read_file"`, and it also narrows the vocabulary to just `tool`.
- **Python gets the mechanism, not the syntax.** No way to rebind name resolution inside a function body, so the DSL object is an explicit parameter: `run(task=..., tools=define_tools)` with `@dsl.tool(...)` inside. Kept `RunDSL` for 1:1 surface parity, but recorded plainly in the README that in Python it earns almost nothing over `@registry.tool(...)` — same shape, and the narrowed surface guards against a mistake nobody makes.
- **`max_output_tokens` uses `or`, not `is None` — the reverse of every previous step's rule.** Ruby's `||` is a truthiness test, so an explicit `0` falls through to the task default. `Agent._call_opts` still guards `0` correctly one layer down; diverging here would make the two languages disagree. Worth noting the rule is "match Ruby's semantics", not "always use `is None`".
- **`logger = None` before the `try`.** Ruby's `ensure logger&.close` works because a local assigned anywhere in a method body exists as `nil` from parse time; Python would raise `UnboundLocalError` if construction failed first.
- **`turn(n:)` and `subscribe` are both added and both dead** — nothing calls either. `log_viz`'s parser already handles a `turn` phase, and the TUI step is the obvious consumer of `subscribe`. Ported anyway, partly because `subscribe` changes `write_log`'s behaviour for every event.

- Mirrored it anyway — the Ruby is the spec, and a Python tree that stayed "ahead" would make every later diff harder to read. But **"what changed between step N and N+1" is not always "what the author intended to change"**, and a diff-driven port has to be able to tell those apart.

### Two verification failures, neither of them the port

- **A check failed identically in both languages — because it was self-referential.** The escape-check in `jsonl_diff.py` looked for the two characters `\u`. The agent's `read_file` tool reads the step README, and the README documents the check, so the literal text `` `\u` `` became test data and JSON stored it as an escaped backslash. Fixed with a negative lookbehind matching a real `\uXXXX`. **A verification suite whose own documentation is inside the system under test can trip on itself.**
- **One check I wrote was fake:** "logger closed on success" ended in `or True`, so it passed unconditionally. Replaced with a spy counting `close()` calls, plus a third case — no logger is constructed at all when backend selection fails first. A check that cannot fail is worse than no check, because it reads as coverage.
- Also caught mid-run: the Python banner said `boukensha.run` where Ruby says `Boukensha.run`. Precedent is to match Ruby verbatim — `Config.__str__` already emits `#<Boukensha::Config …>` in Python for exactly this reason.
- Verified: prefix diff identical (4 lines); JSONL structural diff clean; 36 offline `run()` wiring checks; 11 logger checks for `turn`/`subscribe`; step-06's loop suite still 25/25 and its logger suite 27/29 — the two failures being its assertions that `LoopError` and `mud_*` are *absent*, which step 07 deliberately reverses.
- **`log_viz` renders the iterations bar (25) for the first time**, because `session_start` finally carries `max_iterations`. `max_turn_tokens` and `context_window` are still absent, so those two bars stay hidden until step 12 — exactly as predicted in the morning's log_viz reading.
