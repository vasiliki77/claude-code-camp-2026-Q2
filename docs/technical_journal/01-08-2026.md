## Hypothetical: the same agent on GCP Agent Engine

Not something being built — asked to understand how the managed path differs.

- **Trace Explorer is read-only.** Nothing is manipulated there; every attribute has to be attached in-process before the span is exported. Trace Explorer's role is that span attributes become the filter/group/chart dimensions.
- Agent Engine / ADK auto-instruments via OpenTelemetry into Cloud Trace: spans named `invoke_agent`, `call_llm`, `execute_tool`, `generate_content`, carrying `gen_ai.agent.name`, `gcp.vertex.agent.invocation_id`, `gcp.vertex.agent.event_id`. Enabled by `GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true` (newer) or `enable_tracing=True` on the constructor (older examples).
- Two ways to add to a tree you didn't create:
  - **Decorate the active span** — `trace.get_current_span().set_attribute(...)` inside a tool. ADK's span is current, so it just works. For facts *about* an existing step; adds no rows to the waterfall.
  - **Open a child span** — `tracer.start_as_current_span("validate_order")`. For work with real duration worth isolating. Nests automatically via context propagation.
- **Naming:** use `gen_ai.*` semconv where one exists (that's what makes the built-in dashboards light up), own prefix for everything else. Never a bare `region` or `cost` — unprefixed keys collide with platform-reserved ones. `gen_ai.*` was still experimental and churning; pin to a spec version actually read.
- Three gotchas: **attribute limits** (capped per span, long values truncated — a full prompt body will not survive as an attribute; put it in logs correlated by trace id); **sampling** (an attribute set is not guaranteed present on any given request, so billing/audit data must not live only on a span); **cardinality** (a session id is fine to filter one trace by, expensive as a chart grouping).
- **Takeaway:** `task` / `provider` / `model` / `cost_usd` are already exactly what "custom span attributes" means on a managed platform. The plumbing is what Agent Engine takes over; the judgment about which facts are worth attaching is the part that transfers — and sampling is why the JSONL logger wouldn't be redundant even on a fully-traced platform.

Sources: [Trace an agent](https://docs.cloud.google.com/agent-builder/agent-engine/manage/tracing), [Instrument ADK applications with OpenTelemetry](https://docs.cloud.google.com/stackdriver/docs/instrumentation/ai-agent-adk), [Cloud Trace observability for ADK](https://adk.dev/integrations/cloud-trace/), [ADK Traces](https://adk.dev/observability/traces/), [Gemini Enterprise Agent Platform tracing](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/tracing).

## Step 7 (The Run DSL)

- **`run_dsl.rb` is 13 lines and is not the step.** The step is the ~80-line `Boukensha.run` added to `lib/boukensha.rb`, which collapses the example from 92 lines to 34. `RunDSL#tool` is a pure passthrough to `Registry#tool` — it adds no behaviour.
- **What the block is actually for:** `run` must build the `Registry` itself (it attaches to the `Context` that `run` also builds), but the caller knows which tools they want, and they must be registered *before* the PromptBuilder serialises them. The block is the handoff at that one moment. `instance_eval` is a separate concern — it rebinds `self` so tools read as a bare `tool "read_file"`, and it also narrows the vocabulary to just `tool`.
- **Python gets the mechanism, not the syntax.** No way to rebind name resolution inside a function body, so the DSL object is an explicit parameter: `run(task=..., tools=define_tools)` with `@dsl.tool(...)` inside. Kept `RunDSL` for 1:1 surface parity, but recorded plainly in the README that in Python it earns almost nothing over `@registry.tool(...)` — same shape, and the narrowed surface guards against a mistake nobody makes.
- **`max_output_tokens` uses `or`, not `is None` — the reverse of every previous step's rule.** Ruby's `||` is a truthiness test, so an explicit `0` falls through to the task default. `Agent._call_opts` still guards `0` correctly one layer down; diverging here would make the two languages disagree. Worth noting the rule is "match Ruby's semantics", not "always use `is None`".
- **`logger = None` before the `try`.** Ruby's `ensure logger&.close` works because a local assigned anywhere in a method body exists as `nil` from parse time; Python would raise `UnboundLocalError` if construction failed first.
- **`turn(n:)` and `subscribe` are both added and both dead** — nothing calls either. `log_viz`'s parser already handles a `turn` phase, and the TUI step is the obvious consumer of `subscribe`. Ported anyway, partly because `subscribe` changes `write_log`'s behaviour for every event.

### The change: two keys instead of one path

- `KEY=value` lines keyed by **the same names as the env vars**, so the rc file reads as "defaults for the env vars" rather than a second vocabulary. Blank lines and leading-`#` comments skipped; comments are *not* stripped mid-line, since a path may contain `#`.

### This one diverges from the instructor

- **`resolve` is byte-identical across steps 09, 10, 11 and 12** — same hash for all four. Each later step ships its own `boukensha_loader.rb`, so this is re-applied by hand at 10, 11 and 12 — with a `gem build`/`gem install` each time the global command should reflect it.
- **The precedent for the precedence rule is the instructor's own**, in step 12: *"Legacy env-var override still works and takes precedence over config."* Same env-beats-file rule as `||=` here, so the change extends a pattern already being taught rather than inventing one.
- **A simpler fix existed and was rejected knowingly:** `export BOUKENSHA_DIR=…` in `~/.bashrc` clears the error with zero code change and zero divergence. Took the loader change because the goal is a command that works from any directory *without* ambient shell state, but the cheap option is the one to fall back to if re-applying across 10–12 gets tiresome.
- **Counter-argument worth keeping:** the loader's single job is picking a lib path; `BOUKENSHA_DIR` belongs to `Config`. Exporting it from the loader puts config-dir knowledge in two places, and that split ownership is the likely reason the line was drawn where it was.

## Python has no step 9, and does not need one

- **Python stops at `08_the_repl_loop`; Ruby runs to 12.** Instructor is not porting the global executable, which is correct — step 09 is not an agent feature but a Ruby *packaging* lesson (gemspec, `bin/` shebang, `gem build`/`gem install`, plus a loader that exists only to choose between twelve numbered teaching folders). There is nothing to translate; the Python analogue would be `pyproject.toml` + `[project.scripts]`, a different toolchain lesson.
- **The Python side already solves the half that mattered.** `bin/python/*` sets `: "${BOUKENSHA_DIR:="$REPO_ROOT/.boukensha"}"` — same `:=` precedence as `bin/ruby/*` — and `config.py:77` reads it exactly as Ruby does. Which is why the `tasks.player.model` error has never appeared on the Python side.
- **`bin/ruby/08_the_repl_loop` would have run the REPL with correct config all along.** The global command earns its keep differently: it works from *any* directory, where the launchers only work inside the repo.

### Extracting the two agents after the bootcamp

- **For reuse, the installable package is the deliverable and the global command is nearly free.** `boukensha/__init__.py` already exposes a deliberate public API (`Agent`, `Client`, `Registry`, `Tool`, `run`, `repl`) on two dependencies (`python-dotenv`, `PyYAML`). One `pyproject.toml` yields both the importable library and a `[project.scripts]` console entry point.
- **The loader should not be ported at extraction time either.** `BOUKENSHA_PATH`, step resolution and `BUNDLED_LIB` exist to choose among twelve libs; an extracted package has one. Porting it would bake the bootcamp's shape into unrelated apps — and by the same argument today's `.boukensharc` change is scaffolding with an expiry date, not a feature to carry out.
- **The piece actually worth designing is project-local config discovery** — walk up from the cwd for `.boukensha/`, fall back to `~/.boukensha`, the way git finds `.git`. That replaces `BOUKENSHA_DIR`-by-hand and is worth more than the executable. The `bin/*` launchers already hardcode this idea by pointing at the repo root; discovery makes it automatic. Note Ruby's `Config#resolve_dir` went three-tier at step 08 (`BOUKENSHA_DIR` → `./.boukensha` → `~/.boukensha`) — that is tier 2 of the same idea, without the upward walk.
- **Do it from the final state, not mid-bootcamp.** Python is at 08, Ruby at 12, `week2_capable/` is empty.
- **Open question, flagged not decided:** two parallel implementations is real ongoing maintenance, and in practice one becomes primary while the other drifts into a reference. Worth choosing deliberately rather than discovering it.
