# Week 1

## Technical Goal

Instructor's stated goal (Week 1 Plan slide):

Build the **Baseline Agent** — a custom agent architecture that implements every part of an agent (config, registry, prompt building, API client, agent loop, logging, run DSL, REPL loop, global executable, standard tool library, TUI, context management — the `week1_baseline/ruby/00_config` through `12_context` steps) without using an Agent SDK.

Deliberately not using an Agent SDK so we can:
- Learn how all the parts work.
- Avoid an SDK's genericity/bias — SDKs tend to be tightly coupled to a specific provider or library, which may not suit our use case.

Gameplan:
- Get each step of the agent working in Ruby first.
- Port the working code to our language of choice (e.g. Python).
- Update the Agent Baseline Architecture Diagram after each step.

Once finished, this baseline agent becomes the "golden template" to reuse whenever building an agent going forward.

## Technical Uncertainty

- Whether hand-rolling REST calls to five separate LLM backends (Anthropic, OpenAI, Gemini, Ollama, Ollama Cloud) behind one normalized shape is worth the complexity it adds versus using an SDK — the plan deliberately avoids SDKs to avoid their genericity/bias, but that means absorbing every provider's own request/response schema by hand.
- Whether a config-driven `.boukensha/` directory (settings, secrets, prompts, session logs) will hold up structurally as more steps layer on top of `00_config`, or whether early schema choices will need reworking later.
- Whether the Ruby `MudManager` gem can be reused as-is from a Python port later in the week, given the plan is to build in Ruby first and port afterward.
- Whether avoiding third-party libraries (per the "standard library first" design constraint) is sustainable — `dotenv` was already an early exception.

## Technical Hypotheses

- Building every agent component from scratch (config, registry, prompt building, API client, loop, logging, DSL, REPL, global executable, tool library, TUI, context management) will surface exactly how each part works in a way that an Agent SDK would hide.
- A `~/.boukensha`-style external config directory, overridable via `BOUKENSHA_DIR`, is the right shape for something meant to be deployable on multiple servers.
- Getting each step working in Ruby first, then porting to Python, will make the porting step mostly mechanical since the underlying design won't change — a hypothesis Week 0 already partly refuted for a different kind of port (skill → subagent), worth watching for whether the same holds here.

## Technical Observations

Day-by-day detail is in [24-07-2026](24-07-2026.md), [27-07-2026](27-07-2026.md), [28-07-2026](28-07-2026.md), [31-07-2026](31-07-2026.md), [01-08-2026](01-08-2026.md), [02-08-2026](02-08-2026.md) and [04-08-2026](04-08-2026.md). Summary so far:

- **Step 0 (Configuration)** — first run of `week1_baseline/bin/00_config` failed twice before working: once on a missing `dotenv` gem (`bundle install` fixed it), once on a config file that was both misnamed (`settings.yml` instead of the `settings.yaml` the code looks for) and misplaced (repo root instead of the directory `BOUKENSHA_DIR` actually resolves to). The underlying failure — `Config` silently returning `{}` when no settings file is found, rather than erroring — meant the real problem (file not found) surfaced several calls later as an opaque `NoMethodError` on `nil`, not as a config error.
- **Step 1 (Struct Skeleton)** — ported the three plain data containers (`Tool`, `Message`, `Context`) from Ruby to Python. Ruby `Struct`s became Python `@dataclass`es; `Context` stayed a plain class in both. The port was applied as the delta between step 0 and step 1 (the step-1 Python folder started as a copy of the step-0 one), which bore out the earlier hypothesis that porting is mostly mechanical when the design doesn't change. Verification is a literal `diff` of the Ruby and Python example output, which is empty — the byte-for-byte match required matching Ruby's `to_s` exactly (inclusive-range off-by-ones, an always-appended `...`, and Ruby symbol-form key rendering `[:direction]`).

- **Step 2 (The Tool Registry)** — ported `Registry` and `UnknownToolError`, again as a delta over the previous step's Python folder, again verified by an empty `diff` of the two programs' output. This step is the first place the "porting is mostly mechanical" hypothesis bent: two constructs had no direct Python equivalent and needed a design decision rather than a translation. Ruby registers a tool by passing a block, which became a Python decorator (`Registry.tool` returns a decorator that registers the function and hands it back unchanged). And Ruby's `dispatch` must convert string keys to symbols before calling the block — a gotcha the Ruby README calls out as a real production concern — which **disappears entirely** in Python, where keyword arguments are already strings. The port is therefore not just a different spelling of the same code; one of the lessons the Ruby step exists to teach does not exist in the target language, and the Python README had to say so explicitly to avoid contradicting the Ruby one.
- **Documentation drifted from code, and only running it caught that.** The Ruby step-2 README's "Expected Output" block does not match what the Ruby program prints (it shows a `budget=8192` field that no longer exists and omits the `Config:` line). Since the port's whole verification strategy is diffing against Ruby's real stdout, the expected output had to be captured by running the Ruby example rather than read from its documentation.

- **Step 3 (Prompt Builder)** — ported `PromptBuilder`, `Backends::Base` and five backends. Stdout `diff` still empty, but the example exercises only Anthropic, so verification was extended: all five backends' payloads, headers, URLs and cost metadata dumped from both languages and diffed. The recurring theme of this step is that Ruby and Python disagree on truth. Ruby's `0.0` is truthy, Python's is falsy, so `estimate_cost`'s guard had to become `is None` or every free local model would report an unknown price.

- **Step 4 (API Client) — the byte-for-byte stdout gate stopped working.** The example now makes a live API call, so its output is non-deterministic and billable; two correct implementations produce different bytes. Verification had to be rebuilt around what *is* deterministic: a fixed-length prefix diff, a response key-set comparison, a free 401 exercising the error path, and an offline HTTP server covering retry/backoff. This is the first step where "diff the two programs" — the strategy every earlier step relied on — is simply unavailable, and it will stay unavailable for the rest of the week.

- **Step 5 (Agent Loop) — the delta was much larger than the new file suggested.** `agent.rb` is new, but all five backends changed too, and the loop only stays simple *because* they did: every provider now normalizes its response into one shape, so the agent never sees a raw provider payload. Two Ruby-vs-Python truthiness differences sat in the critical path, and one was dangerous — `wrap_up` disables tools by passing an empty list, which is falsy in Python, so the obvious port would have re-enabled every tool during the one call whose purpose is to stop the agent, silently defeating the iteration ceiling.

- **The cheap cross-language check keeps finding real bugs.** Feeding canned provider responses through both implementations and diffing the JSON caught a wire-format defect in step 5: Ruby's `#to_json` is compact, Python's `json.dumps` is not, and that string is OpenAI's `function.arguments`. The Anthropic-only example would never have surfaced it. Pattern confirmed over three steps: whatever the example does not exercise needs its own throwaway gate.

- **Two upstream Ruby bugs found and left unfixed.** `PromptBuilder#to_messages` is broken for three of five backends (arity mismatch) and survives unchanged to step 12. `PROMPTS_DIR` resolves outside the step folder to a directory that does not exist, in every step from 04 to 11, masked only because the player task overrides its prompt. Ruby is upstream and is not edited during a port; the first was mirrored, the second was fixed on the Python side by decision.

- **Step 6 (The Logger) — the verification artifact stopped being stdout.** Every `puts` left the agent loop, so the example's output shrank to a header and a final response, while the thing the step actually produces became a `.jsonl` file. The prefix diff got *stronger* and simultaneously stopped covering the subject. Verification was rebuilt around a structural diff of the two languages' session logs — phase sequence, key list, and **key order** per event, with ids, timestamps, token counts and free text normalised away. This is the second time in the week the gate had to be redesigned rather than extended (step 4 was the first), and the pattern is now clear: each step's verification has to be derived from what that step *produces*, not inherited from the previous one.

- **Serialisation details are where a "mechanical" port actually bleeds.** Matching Ruby's JSONL byte-for-byte needed four separate non-obvious decisions: compact separators, `ensure_ascii=False` (Ruby emits raw UTF-8; the agent logs an em dash), `timespec="seconds"` (Ruby's `iso8601` has no fractional seconds, Python's `isoformat` defaults to microseconds), and deliberate dict-construction order, since key order is part of the output. None of these are visible in the design; all are visible in a diff.

- **Two language-forced structural divergences, both documented rather than hidden.** Python needed a `runtime.py` module that Ruby has no equivalent of, because Ruby resolves `Boukensha.config` at call time while the literal Python transcription is a circular import. And step 7's `instance_eval` — which rebinds `self` so the Ruby DSL reads as a bare `tool "read_file"` — has no Python equivalent at all, so the DSL object became an explicit parameter. Python gets the mechanism (a handoff at the moment the registry exists) and loses the syntax. Worth being honest that `RunDSL` consequently earns very little in Python: `@dsl.tool(...)` and `@registry.tool(...)` are the same shape.

- **The rule was never "always use `is None`".** Steps 3–6 each hit a Ruby-vs-Python truthiness difference where the fix was an explicit `is None` check. Step 7 inverts it: `Boukensha.run`'s `max_output_tokens || task_default` is a truthiness test in Ruby, so an explicit `0` *should* fall through to the default, and the faithful port is `or`. The actual rule is "match Ruby's semantics", and four consecutive steps of the same fix had started to look like a general one.

- **The Ruby steps are not a linear progression, which a diff-driven port has to be able to detect.** Three things step 6 deleted are restored in step 7 in their pre-step-6 form: `LoopError`, `Config`'s four `mud_*` readers, and `context.rb`'s alignment. `07/errors.rb` is byte-identical to `05/errors.rb`, and `07/config.rb` also reverts step 6's `@dir =` alignment and its one-line `load_env` guard — so step 7 appears branched from around step 4/5 rather than from step 6. Mirrored anyway (the Ruby is the spec), but it means *"what changed between step N and N+1"* is not always *"what the author intended to change"*.

- **Two verification failures that were defects in the checks, not the code.** An escape-check failed identically in both languages because it was self-referential: the agent's `read_file` tool reads the step README, the README documents the check, and the literal text became test data. And one check ended in `or True`, so it passed unconditionally — a check that cannot fail reads as coverage while providing none. Both were found only because the failures were investigated rather than assumed to be port bugs.

- **A path duplicated across thirteen files drifted in four of them, and stayed invisible until a step was actually run.** Every Ruby example resolved the config directory itself, by counting `..` from its own location — a repo-layout assumption copied into thirteen places. `ITERATIONS.md` had anticipated the adjustment needed when the code moved into a `ruby/` sub-folder, but it was only applied to steps 00–07; steps 08, 10, 11 and 12 still pointed one level short, at a directory that does not exist. The same class of bug independently hit `log_viz`, whose default sessions path was one level short in the other direction. Three instances in a day. The fix was to stop repeating the derivation: compute it once in the launcher, where the entry point already knows where it is, and delete the line from every example. **Duplicating a derived value is a slow leak — it does not fail when introduced, it fails later, in whichever copy was missed.** Assigning it with `:=` rather than a plain export preserved the documented user override that the per-file `||=` had been providing.

- **The same silent-fallback design cost diagnosis time twice in one week.** Ruby's `Config#load_settings` returns `{}` when `settings.yaml` is absent instead of raising. On 24-07 that turned a misplaced config file into an opaque `NoMethodError` on `nil` several calls downstream; on 01-08 it turned a wrong directory into `tasks.player.model is required in settings.yaml`, an error naming a settings key when the real problem was that no settings file had been found at all. Both times the actual cause was visible in output already on screen — the `Config:` line printed the wrong directory and an empty task list — and both times it was read past. The Python port raises `FileNotFoundError` naming the directory, which is the behaviour worth keeping. **A fallback that makes a missing input look like an empty input moves the error away from its cause.**

- **Verification cost is not a one-way ratchet — step 8 got back what steps 4–7 lost.** The byte-identical stdout diff died at step 4 when the example started making live calls, and steps 6 and 7 shrank stdout further until it was a header and a final response. Step 8 reversed it: the REPL's banner and its five built-in commands (`/help`, `/quiet`, `/loud`, `/clear`, `/exit`) are byte-identical between the two languages **and never reach the model**, so a piped command script is a free, fully deterministic gate over a real slice of the step. That was structural rather than lucky, and it generalises: **look for the part of a feature that does not touch the non-deterministic dependency, and gate hard on that**, instead of treating the whole feature as untestable because part of it calls an API. The same reasoning is what turned step 6's session log into a diffable artifact once stdout stopped being one.

- **The scratch checks stopped finding port bugs at exactly the point the plans started predicting them.** Steps 3–5 earned their keep — the cross-language dump caught the compact-JSON defect in OpenAI's `function.arguments`, among others. Across steps 6–8 they found **zero** defects in the ported code, while containing four defects of their own: a self-referential escape check that matched its own documentation, an assertion ending in `or True` that could not fail, a helper reaching for state that does not exist on an early-exit path, and a stub that never restored the real method. The cause is not that the checks got worse — it is that writing the traps down in the plan *before* writing the code (the `is None` guards, `ensure_ascii`, timestamp precision, `task_name()`) meant the code was right the first time, so the checks had nothing left to discover. **Their value moved from finding bugs to preventing future ones**, which is still worth paying for — the step 5–7 suites all re-run green against step 8, which is how a regression guard is supposed to look — but it changes what they should be judged on, and it means a check that cannot fail is a genuine loss rather than harmless.

- **Skills were tried for the port workflow and abandoned as too costly and slow.** A `ruby-to-python-port` skill was written, then an A/B evaluation was attempted with two subagents on step 04. Each subagent starts cold and re-derives context the session already holds: the baseline burned 61,235 tokens and ~234 seconds and produced no plan at all, stopping to ask a clarifying question first. Both runs were abandoned with zero artifacts. The baseline also found the same non-obvious problems unaided, so the skill's marginal value was never demonstrated. Writing the plans directly in-session produced steps 04 and 05 for a fraction of the cost. Reusable instructions are not free when the reuse mechanism discards the context that made the work cheap.

- **Step 9 (Global Executable) — packaging created a fourth entry path, and the launcher fix could not reach it.** Installing the gem produced a command that deliberately bypasses `bin/ruby/*`, so the `BOUKENSHA_DIR` derivation just centralised into the launchers did not apply to it, and `boukensha` failed with the same `tasks.player.model is required` message for the same missing-config-directory reason. Two findings behind it: the loader that actually executes is the *installed gem's* copy, not the step folder's — so editing `09_global_executable/lib/boukensha_loader.rb` changes nothing until `gem build` + `gem install` — and `~/.boukensharc` could only express which lib to load, not where the config lives. Extended it to `KEY=value` lines keyed by the env var names, with a bare path still parsing as `BOUKENSHA_PATH`. **This is the week's first deliberate divergence from the Ruby spec:** `resolve` is byte-identical across steps 09–12 and step 12's header still calls the config directory "separate", so the instructor's design holds the line the change crosses; it is applied to step 09 only and must be re-applied by hand at 10, 11 and 12.

- **The port reached a step with nothing to port.** Python stops at `08_the_repl_loop` and step 9 is not being ported, correctly — it is a Ruby *packaging* lesson (gemspec, shebang, `gem build`/`gem install`, plus a loader whose only job is choosing among twelve numbered teaching folders), not an agent feature. The Python analogue would be `pyproject.toml` with `[project.scripts]`, a different toolchain. The half that mattered was already solved on the Python side: `bin/python/*` exports `BOUKENSHA_DIR` with the same `:=` precedence as `bin/ruby/*`, which is why the config error never appeared there. Forward-looking consequence for the "golden template" goal: for reuse the deliverable is the installable package, not the global command, and the loader should be *deleted* rather than ported — an extracted package has one lib, so `BOUKENSHA_PATH` and today's `.boukensharc` change are both scaffolding with an expiry date. The piece worth designing instead is project-local config discovery (walk up from the cwd for `.boukensha/`), of which step 8's three-tier `resolve_dir` is already tier two.

- **"Built" and "installed" are different states, and the repo's own artifacts disguise the difference.** Step 10 would not run: `mud_manager (0.1.0)` was locked but bundler reported *"the author of mud_manager (0.1.0) has removed it"*. Nothing was removed — the gem was never published (`gem list -r -a` empty, rubygems API 404, search `[]`); it is an in-repo gem at `week0_explore/mud_manager/`. `gem build` had been run and `gem install` had not, and the resulting `.gem` file sitting in the folder beside four `boukensha-*.gem` files read as evidence the work was finished. **Third error message this week that named a plausible wrong cause**, after the two silent-`{}` config failures — and, like both of those, the accurate hint was already on screen (bundler's own *"or installed locally"*).

- **Two entry points into the same step disagree, because only one of them invokes bundler.** `boukensha` and `bin/ruby/<step>` are not two doors into the same room: the launcher runs a fixed `examples/example.rb` and exits, under `bundle exec` against that step's lockfile, in the step directory; the global command starts an interactive REPL, on whatever step `~/.boukensharc` selects, resolving gems globally with no Gemfile anywhere in the picture, in whatever directory it was invoked from. That last difference is what cost an afternoon — it is why `mud_manager` had to be installed rather than merely built, and it means the global command silently depends on the globally installed gems agreeing with a step's lockfile. Concretely: `BOUKENSHA_PATH=…/10_standard_tool_library boukensha` works now and still fails for steps 11 and 12, whose nine charm/bubbletea gems are not installed globally. **"Which lib runs" and "which gems are available" are independent questions**; only the first has a resolution order documented anywhere.

- **Every launcher-shaped thing in the repo states a path or a name twice.** A launcher was renamed on a misreading of the numbering — `09_global_executable/README.md` is titled "Step 8", so step *names* trail folder *numbers* throughout, which makes the standard tool library read as "Step 9" when its folder is `10_` — and it broke because the filename and the hardcoded `cd` path are two copies of one fact. Same shape as the thirteen-file `..` duplication and the lockfile-versus-installed-gems mismatch. `bundle check >/dev/null 2>&1 || bundle install` now guards all 12 Ruby launchers so a missing gem installs instead of failing.

- **Exposing the MUD over MCP moved every bug from the code into the signals.** The daemon and its integration mostly worked first time; the day went on things that worked reporting that they did not, and things that were off reporting nothing at all. A stdio server is byte-identically indistinguishable from a hang. A REPL banner derived from one of two mutually exclusive routes confidently described the route that was switched off. A timeout error interpolated its `timeout:` *argument* rather than the value it enforced, printing `after s` and hiding the one number separating "too slow" from "waiting for the wrong thing". And `BOUKENSHA_MCP=1` was ignored in total silence — found only because the banner was lying about something else. **When a component can be reached two ways, the status line is a third thing that can be wrong independently of both.**

- **A capability step 09 built never reached step 10, and nothing in the repo could have said so.** `~/.boukensharc` had been extended from a bare path to `KEY=value` lines at step 09; step 10's loader still read the whole file as one path, so `boukensha` aborted with the rc file's own contents echoed back as the directory it could not find. Because each step folder is a standalone snapshot, "step 10 dropped this deliberately" and "step 10 was written without thinking about it" are indistinguishable from the code — the instructor's term for the class is a **floating artifact**: code a step built that the next step's rewrite did not carry forward. Carried into step 10; **steps 11 and 12 still float**, the third time this same change has been recorded as pending.

- **"Which lib runs" and "which gem is installed" cost an afternoon for the third time.** `BOUKENSHA_MCP=1` did nothing because the installed gem was `boukensha-0.9.0` — which *did* have step 09's rc parser, so the config directory resolved correctly and nothing looked wrong, while the global command ran step 09's loader against step 10's lib. After the counted `..` paths and the built-but-never-installed `mud_manager`, the pattern is settled: **the artifact on disk is routinely newer than the artifact executing, and the resulting failure always names something else.**

- **A login branch that had existed all week only became reachable once there were two ways to connect.** tbaMUD answers a password three ways, not two: besides `Welcome` and `Reconnecting` it may say `You take over your own body, already in use!`, the linkdead take-over path. CircleMUD keeps a character in-world briefly after a disconnect, so running the daemon, exiting, and starting the REPL triggers it reliably — but with only one connection route it had never fired. **Adding a second path to the same resource does not just add its own bugs; it makes the first path's dormant ones reachable.** First edit to `session.rb` since the gem was written, and both lines were about reporting rather than behaviour.

- **Two Ruby behaviours bind to the wrong thing without complaining.** Splatting a trailing hash into `public_send` passes it *positionally* under Ruby 3's strict separation, so every keyword-taking primitive would have raised. And a bare `Client` inside `Boukensha::Tools::Mcp` resolved up the lexical scope to `Boukensha::Client` — the LLM API client — with the subsequent `.spawn` landing on `Kernel#spawn`. **Ruby resolves a shadowed constant silently to the wrong class rather than raising `NameError`**; only the tests caught it, and reading would not have.

- **A failing check was wrong about correct code**, inverting the week's earlier lesson. An assertion counted logins by searching received commands for the character name, but the fake MUD only records lines received *after* authentication, so the count could never be anything but zero. A check that cannot pass is at least loud, where the earlier `or True` could not fail and read as coverage while providing none.

- **Two pre-existing limits were found and deliberately left.** Tool results are coerced with `to_s` before reaching the context, so no MCP server can return an image or resource to the model however well the client handles it; and every tool parameter is advertised as required because the backend builds that list from all parameter keys. Both affect all tools rather than MCP ones, both need their own plan, and bundling either into a refactor would have destroyed the one property that made it reviewable — that the existing assertions did not change.

- **Two plans disagreed with themselves, and one disagreed with this repository.** A plan's written recommendation made the generated spec canonical while its inline reply made Ruby canonical; another deferred multi-session while its reply required it. The replies are newer and win, but nothing in the document says so, and reading top-to-bottom gives the wrong answer twice. Separately, the instructor's follow-up plan assumed two gems, a MUD-specific tool module and a bridge inside the daemon — none of which exist here, because an earlier plan had already been executed differently. About a third of its migration was complete before it was read and one step did not apply at all. **A plan is written against a snapshot; executing it means diffing the snapshot first.**

- **The Python port of step 10 left out its largest file, and that was the point.** `tools/mud.rb` is 480 lines registering 26 MUD tools against a `MudManager::Session`; Python obtains the same 26 by spawning `mud-manager --mcp` and asking what it has. Ruby adds ~1,000 lines of library code in this step, Python needed ~520, and the difference is almost entirely that one file. **This is the first time the daemon's premise was tested by a second language rather than argued for in a plan** — and it held: a Python bootcamper needs a Ruby *runtime*, not a Ruby toolchain, and no Ruby knowledge. The fake MUD was not ported either, for the same reason: it is a server on a socket, and the language it is written in is invisible from the other side.

- **The strongest verification gate of the week came free from the architecture.** Because the daemon is language-neutral, both implementations can drive the *same* `mud-manager` process, so their discovered tool tables must be byte-identical — 26 tools, same names, descriptions, types and enums, no API calls. **A difference there can only be a client bug, never a tool bug**, which makes it unusually good at localising failure. Filesystem and shell tools diffed identically too, error strings included, restoring stdout comparison for a whole subsystem for the first time since step 03. Unlike every earlier gate, this one is a property of the design rather than of the test, so it does not rot when the next step changes what the example prints.

- **A trap filed under where it was found will recur where it wasn't.** The cross-language diff failed twice before passing, both times because the *check* was wrong: Ruby preserves hash insertion order where the Python dump sorted keys, and `json.dumps` escapes an em dash unless given `ensure_ascii=False`. The second is **the same defect step 06 hit** matching the session log — recorded then as a logger lesson, so it was absent from step 10's trap list and reappeared in a completely unrelated artifact. Serialisation differences are not a logging problem; they are a Ruby-vs-Python problem, and they will surface anywhere the two languages' output is compared. Third failing check this week that was wrong about correct code.

- **Traps written into the plan before any code did not become bugs, and the prevention generalised.** The `None`/`False` collapse was predicted — Ruby's `nil` means "use config" and `false` means "skip", both falsy in Python — written up, implemented as identity checks, and tested. More usefully, the *category* being salient caught an instance the plan had not listed: `allowed_commands=[]` means "permit nothing", and `[]` is truthy in Ruby but falsy in Python, so `if allowed_commands` would have silently permitted **everything** when the caller asked to permit nothing. That one passes every test not written for it. Confirms steps 06–08's finding from the other side: **prevention scales better than detection, and it scales beyond the specific cases enumerated.**

- **Porting keeps finding defects in the language being ported *from*.** Ruby's step 10 has lost step 08's 401 error message, the same non-linearity that made step 07 look branched from step 04/05 — kept on the Python side by decision rather than mirrored. And a subprocess leak surfaced that Ruby shares: if session construction fails after the MCP servers spawn, the caller never receives the session, so its cleanup has nothing to close and the children are orphaned. Neither was visible from reading Ruby alone. **A port is a slow, expensive, unusually thorough code review of the original.**

- **Carrying a capability forward destroyed a different one, in the same command.** Step 10's `boukensha_loader.rb` was copied over step 11's to bring the `~/.boukensharc` parsing along; step 11's loader had three lines step 10's did not — the `--no-tui` flag — and they went silently. So one `cp` both fixed a floating artifact and created one. Worse, **my own plan had asserted that file was safe**: it claimed `registry.rb`, `config.rb` and `boukensha_loader.rb` "differ only by the step-10 additions", and I had verified two of the three and generalised. **A whole-file copy is not a delta**, and a claim about a category of files is only as good as the file in it you didn't check.

- **Anything installed, locked, or built is a cache, and each one failed by reporting something other than staleness.** Three more instances in a day, bringing the week to six. A `Gemfile.lock` pinning `mud_manager 0.1.0` surfaced as bundler reporting a missing *executable*. An installed gem built from the window between breaking `--no-tui` and fixing it surfaced as the flag being accepted and ignored, with no error at all. And running `boukensha` inside any step directory double-defines `VERSION`, because bundler evaluates that step's gemspec — which loads its own `version.rb` — before the loader requires a different step's library, so the banner reports a version that is not the code running. **None of the six announced itself as "the thing executing is older than the thing on disk", which is what every one of them was.**

- **Two bugs in one hand-applied delta is an argument about method, not about care.** Besides the loader, a helper (`close_mcp_clients`) fell outside the range the extraction script copied and both `ensure` blocks called a method that did not exist — invisible to the tests, which never call `Boukensha.repl`, and caught by a five-second smoke run. The delta plan had already asked whether the remaining steps should be regenerated from step 11 rather than patched independently; two defects in the first application is the evidence that question was waiting for.

- **A one-line Ruby-vs-Python difference held up the whole verification strategy.** Step 11's only fully deterministic gate is the plain `tui=False` REPL diffed byte-for-byte against step 10 — a full-screen app is not diffable. That gate survives only because `_output` reimplements Ruby's `puts`, which leaves an existing trailing newline alone where Python's `print` adds a second. Every banner would otherwise have lost a blank line and the gate with it. **The cheapest detail in the step was load-bearing for its most valuable check.**

- **A crash on quit existed the whole time and only the test harness's rhythm exposed it.** Textual keeps firing its interval during teardown, when the widgets it queries are gone. Every test passed individually; the suite failed, because suite timing lands a tick inside the teardown window and interactive use usually does not. This is the inverse of a flaky test — **the same timing sensitivity that usually produces false failures produced a true one**, and only because the harness ran differently from a human.

- **Some divergences are capability gaps and should be written down as such.** Ruby cancels a turn with `Thread#raise(Interrupt)`, which lands wherever the thread is, including inside a blocking read; Python's nearest equivalent only fires when the thread next returns to bytecode, so it cannot cut short an in-flight request — it would take effect exactly when it stops mattering. Shipping a `ctypes` version would have *looked* like the Ruby behaviour and failed silently in the only case worth cancelling. Cooperative cancellation plus a documented gap is the honest port; **matching an API is not the same as matching a behaviour, and pretending otherwise is worse than the gap.**
