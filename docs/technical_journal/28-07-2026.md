## Step 2 (The Tool Registry) — Ruby → Python Port

- Wrote the port plan at `docs/plans/python_port/02_the_registry`, then implemented it. Step 2 adds the `Registry` — the object that stores tools and dispatches them by name — plus a dedicated error class. The agent never calls a tool directly; it names one, and the registry looks it up and runs it.
- Same pattern as step 1: the Python step folder already existed as a byte-for-byte copy of `python/01_struct_skeleton` (`diff -rq` empty), so the work was applying only the delta Ruby made between steps 1 and 2, not a port from scratch.
- **Ruby's own delta was five files:** new `lib/boukensha/registry.rb` and `lib/boukensha/errors.rb`, two added `require_relative` lines in `lib/boukensha.rb`, a rewritten `examples/example.rb`, and a rewritten `README.md`. Everything else (`config.rb`, `tool.rb`, `message.rb`, `context.rb`, `tasks/*`, `Gemfile`) is byte-identical between the two Ruby steps, so the copied Python equivalents needed no touching.

### Design decisions

- **Ruby block → Python decorator.** Ruby registers a tool by passing a block (`registry.tool("shout", ...) do |message:| ... end`). Python has no block syntax, so `Registry.tool` returns a decorator and the decorated function is the tool's callable. The decorator returns the function unchanged, so registration is a pure side effect and the function stays directly callable. Chosen over passing a lambda as a keyword argument; the instructor's implementation used the decorator too.
- **Ruby's symbol-key conversion has no Python equivalent.** Ruby's `dispatch` does `args.transform_keys(&:to_sym)` because the API returns string-keyed JSON while Ruby blocks take symbol keywords — the Ruby README flags this as a production gotcha. Python keyword arguments *are* strings, so `dispatch` calls `tool.block(**args)` on the API's dict directly. The whole translation step disappears. Recorded in the Python README so the two READMEs don't appear to contradict each other, and pinned by a `grep` in the verification list so it can't get cargo-culted back in later.
- **`StandardError` → `Exception`** for `UnknownToolError`, not `BaseException` (which would slip past ordinary `except` handlers).
- **No mutable default arguments** — `parameters=None` / `args=None` with `or {}` at the call site, rather than Ruby's literal `parameters: {}` / `args = {}` defaults.
- **`self.context` public** (Ruby uses `@context` with no reader, effectively private) — later steps are likely to read the context back off the registry.
- **No argument validation in `dispatch`** — Ruby doesn't validate that `args` keys match the declared `parameters`, so neither does the port. Keeps the step small and the failure mode identical.

### Findings

- **The Ruby step-2 README's "Expected Output" block is stale.** It shows `#<Context turns=0 tools=2 budget=8192>` and omits the `Config:` line entirely; the code prints neither. Caught by running the Ruby example instead of trusting the README. Expected output for the port was captured from the real run. Left unfixed on the Ruby side — flagged as out of scope for a Python port.
- **An uncommitted Ruby fix was deliberately not ported.** `ruby/02_the_registry/examples/example.rb` had a working-tree change moving `BOUKENSHA_DIR` from `../../../.boukensha` to `../../../../.boukensha` — a Ruby-side path-depth bug. The Python example already resolved the repo root correctly via `parents[4]`, so porting the "fix" would have broken it.
