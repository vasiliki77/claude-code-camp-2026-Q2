# 04-08-2026

Building the MCP layer for `mud_manager`, then reworking it to the instructor's design, then porting step 10 to Python. Almost every problem in the first half was a *signal* problem — something that worked reporting that it didn't, or something broken reporting nothing at all. The second half had almost no problems at all, which turned out to be the interesting part.

## Three things that looked broken and weren't, and one that looked fine and wasn't

- **A stdio server is indistinguishable from a hang.** `mud-manager --mcp` at a shell prompt prints nothing and waits on stdin forever. That is exactly correct — it is a subprocess an agent spawns, not a program a human runs — but the observable behaviour of "working" and "frozen" is byte-identical.
- **The REPL banner reported the opposite of the truth.** The MCP path deliberately disables the in-process MUD tools, and the banner reads that flag, so it printed `mud: (not configured)` while 26 MUD tools sat registered and working. **A status line derived from one of two mutually exclusive routes will confidently describe the route that is switched off.**
- **A timeout error printed the wrong number.** `Session#read_until` interpolated its `timeout:` *argument* rather than the value it enforced, so every caller relying on the default got `after s`. That is the one number separating "too slow" from "waiting for the wrong thing", and its absence cost real diagnosis time before it was noticed as a bug rather than a formatting quirk.
- **The one that looked fine:** `BOUKENSHA_MCP=1 boukensha` printed a normal banner, booted normally, and silently ignored the variable entirely. No error, no warning. Diagnosed only because the banner said the wrong route — the misleading signal from two bullets up is what exposed the silent one.

## `~/.boukensharc`: step 09 built it, step 10 never received it

- **Running `boukensha` aborted with the rc file's own contents echoed back as if they were a path.** Step 09 had extended `~/.boukensharc` from a bare path to `KEY=value` lines; step 10's loader still did `File.read(rc).strip` and treated the whole multi-line file as one very long directory name. `File.expand_path` does not raise on that — it just yields a directory that cannot contain `lib/boukensha.rb`.
- **Nothing marked the capability as dropped rather than forgotten.** Each step folder is a standalone snapshot, so "step 10 no longer parses KEY=value" and "step 10 was written without thinking about it" are indistinguishable from the code. The instructor has a name for this class — a *floating artifact*: code a step built that the next step's rewrite did not carry forward.
- Carried the parser forward into step 10. **Steps 11 and 12 still float** — third time this same change has been noted as pending.

## "Which lib runs" and "which gem is installed" are still two questions

- **`BOUKENSHA_MCP=1` did nothing because the installed gem was `boukensha-0.9.0`.** It had step 09's rc parser — which is why the config directory resolved correctly and nothing looked wrong — but predated the MCP switch. So the global command ran step 09's *loader* while loading step 10's *lib*.
- **Third instance of this shape this week**, after the counted `..` paths and the built-but-never-installed `mud_manager`. Every time, the artifact on disk was newer than the artifact actually executing, and every time the failure named something else.

## `Session#login` had a third case nobody had met

- **tbaMUD answers a password three ways, not two.** Besides `Welcome` and `Reconnecting` it may say `You take over your own body, already in use!` — the linkdead take-over path. The login regex matched neither, so it waited the full timeout and failed.
- **It only became reachable once there were two ways to connect.** CircleMUD keeps a character in-world briefly after a disconnect, so running the daemon, exiting, and immediately starting the REPL reliably triggers it. The bug had existed all along with nothing to expose it.
- **First edit to `session.rb` since the gem was written.** Two lines, both about reporting: one pattern, one error message.

## Two Ruby behaviours that bind to the wrong thing without complaining

- **Splatting a trailing hash into `public_send` passes it positionally.** Ruby 3 separates positional and keyword arguments strictly, so `*[:method, {target: x}]` reaches a keyword-only method as a positional Hash and raises — for every one of the primitives that takes keywords. Caught before running, but only by reading rather than by testing.
- **A bare constant resolved up the lexical scope to a different class.** Inside `Boukensha::Tools::Mcp`, `Client` found `Boukensha::Client` — the LLM API client — rather than the MCP one, and the subsequent `.spawn` landed on `Kernel#spawn`. **Ruby resolves this silently to the wrong class instead of raising `NameError`**; the tests caught it, reading would not have.

## A failing check that was wrong about the code

- **An assertion counted logins by looking for the character name among received commands.** The fake MUD only records lines received *after* authentication, so the count was always zero. The code under test was correct; the check was measuring something that could not exist.
- Same lesson as the `or True` assertion earlier in the week, inverted: a check that cannot pass is at least loud, where a check that cannot fail is silent.

## Precedence that held on one path and inverted on the other

- **Forwarding config into a child process overrode inherited environment variables**, reversing the documented rule that env wins over config. It broke only on the MCP path — the in-process path still honoured the variable — so the two routes to the same tools would have disagreed about which credentials to use, with nothing reporting a conflict.

## Limits found and deliberately not fixed

- **Tool results are Strings all the way down.** The agent loop coerces every result with `to_s` before it reaches the context, so no MCP server can ever return an image or a resource to the model, however well the client handles it. Fixing that touches the context, the agent, and all five backends.
- **Every tool parameter is advertised as required**, regardless of intent, because the backend builds the required list from all parameter keys. Harmless against our own schemas, and a genuine defect against third-party ones.
- Both were left alone. They are pre-existing, they affect all tools rather than the MCP ones, and bundling them into this work would have made a refactor unreviewable.

## The plans disagreed with themselves, and with this repository

- **A plan's body and its inline replies recommended opposite things.** The written recommendation made the generated spec canonical; the inline answer made Ruby canonical. Another pair deferred multi-session while the reply required it. The replies are newer, so they win — but nothing in the document says so, and reading it top-to-bottom gives the wrong answer twice.
- **The instructor's follow-up plan assumed a starting state this repo does not have.** It expected two gems, a MUD-specific tool module and a bridge living in the daemon; here the gems were already merged and the bridge was already generic. Roughly a third of its migration was complete before it was read, and one step did not apply at all. **A plan is written against a snapshot; executing it means diffing the snapshot first.**

# Porting step 10 to Python

## The largest file in the step was deliberately not ported

- **`tools/mud.rb` is 480 lines and has no Python counterpart.** It registers 26 MUD gameplay tools by hand, each driving a `MudManager::Session` held in a closure. Python gets the same 26 by spawning `mud-manager --mcp` and asking what it has.
- **This is the first time the daemon's whole premise was tested by a second language**, rather than argued for in a plan. Ruby adds roughly a thousand lines of library code in this step; Python needed about 520, and the difference is almost entirely that one file.
- Python needs the `mud-manager` **binary**, not the gem as a library — a Ruby runtime, not a Ruby toolchain, and no Ruby knowledge to run it.
- **The fake MUD was not ported either.** The tests drive the Ruby `FakeMud` as a subprocess. It is a server on a socket; the language it is written in is invisible from Python, which is the same argument that let `tools/mud.rb` stay behind. Two fakes agreeing on the CircleMUD login dance would be a second thing to keep in sync for no gain.

## The verification got stronger, for a structural reason

- **Both languages can drive the *same* `mud-manager` process**, so their discovered tool tables must be byte-identical — 26 tools, same names, descriptions, parameter types and enums. No API calls, no model, fully deterministic.
- **A difference in that diff can only be a client bug, never a tool bug**, because both sides got the table from one server. That makes it unusually good at localising failure, and it is the strongest gate available since step 03.
- The filesystem and shell tools diff identically too, error strings and the path-traversal refusal included — the first time since step 03 that a whole subsystem could be gated on stdout again.
- **The gate exists only because the daemon is language-neutral.** It is a property of the architecture rather than of the test, which is the sort of verification that does not rot.

## The check was wrong twice before the code was wrong once

- **First failure: key ordering.** Ruby preserves hash insertion order; the Python dump sorted the inner keys and the Ruby one did not. Every parameter appeared to differ.
- **Second failure: `ensure_ascii`.** Two tool descriptions contain an em dash. Ruby emits raw UTF-8; `json.dumps` escapes it to `—` unless told otherwise. **This is the same trap step 06 hit** matching the session log byte-for-byte — recorded then as a logger lesson, so it was not on this step's list, and it recurred in a completely different artifact.
- **Third time this week a failing check was wrong about correct code.** The pattern is now clear enough to name: **a trap recorded as a lesson about one artifact will recur in another, because the note was filed under where it was found rather than under what causes it.** Serialisation differences are not a logging problem; they are a Ruby-vs-Python problem, and they will keep appearing wherever the two languages' output is compared.

## The traps written down in advance did not become bugs

- **The `None`/`False` collapse was predicted and did not happen.** Ruby distinguishes `nil` (use config) from `false` (skip entirely); both are falsy in Python, so `if not mcp` would have silently merged them. Written into the plan before any code, implemented as `is None` / `is False`, and covered by a test.
- **The same shape appeared where the plan had not predicted it**, and was caught because the plan had made the *category* salient: `allowed_commands=[]` means "permit nothing", and `[]` is truthy in Ruby but falsy in Python. `if allowed_commands` would have silently permitted **everything** when the caller asked to permit nothing — a security-shaped bug that passes every test not written for it.
- This repeats step 06–08's finding from the other direction: **writing traps down in advance moves the value from finding bugs to preventing them**, and the prevention generalises beyond the specific instances listed.

## Porting found bugs in the source language

- **Ruby step 10 had lost step 08's 401 handling** — `authentication failed (401) — check your API key` exists in step 08's `client.rb` and not in step 10's. Same non-linearity that made step 07 look branched from step 04/05. Kept on the Python side by decision rather than mirrored.
- **A subprocess leak that Ruby also has.** If session construction fails *after* the MCP servers are spawned — an unknown backend, say — the caller never receives the session, so its cleanup block has nothing to close and the child processes are orphaned. Found only because Python's construction path had to be re-read line by line. **Porting is a slow, expensive code review of the original**, and this is the second defect it has surfaced in Ruby that reading Ruby alone did not.

## Two things that were already right

- **Python's `_build_session` had been factored out at step 08**, where Ruby still copy-pastes the same ~45 lines into `run` and `repl`. The new wiring — working directory, shell options, MCP registration — landed in one place instead of two. A port decision made two steps ago paying off.
- **`Registry` already exposed its context.** Ruby needed an `attr_reader` added so the MCP bridge could detect tool-name collisions; Python's equivalent has been a plain public attribute since step 02, so there was nothing to change.

## Smaller notes

- **The version had to be bumped 0.8.0 → 0.10.0.** The folder is a copy of step 08 and step 09 is skipped, so the number jumps two — the first step where Python's version is not one behind its own folder number.
- Step 09's Ruby artifacts (`boukensha_loader.rb`, the gemspec, `bin/`) sit in Ruby's step 10 folder because it inherited them. None are ported, and the README says so, otherwise the absence reads as an unfinished port later.
- **First Python step with a real `test/` directory.** Verification has lived in throwaway scratch scripts since step 03; the cross-language gates are worth keeping, so they became 38 unittest cases.

# Carrying step 10 into step 11, and porting step 11

## I created a floating artifact while remediating one

- **Copying step 10's `boukensha_loader.rb` over step 11's destroyed step 11's `--no-tui` flag.** Three lines — `ARGV.delete("--no-tui")` and the `tui:` option it feeds — silently gone.
- The file I overwrote it with was the one carrying step 09's rc-file parsing *forward*. So the same operation fixed a capability step 10 had lost and destroyed one step 11 had gained, in a single `cp`.
- **My own plan asserted this file was safe.** It said `registry.rb`, `config.rb` and `boukensha_loader.rb` "differ **only** by the step-10 additions — step 11 has no competing changes in any of them." I had actually diffed the first two and assumed the third matched because it was in the same category. **A claim covering three files was verified for two.**
- Found only because running `boukensha` produced a version banner that prompted a look at the loader. Nothing else would have surfaced it: no test covers the flag, and the flag's absence looks exactly like the TUI working as designed.

## A helper that fell outside the extraction range

- **`close_mcp_clients` was not copied.** The script lifting the new helpers took everything between the `MUD_PREFIX` marker and `mud_opts_from_config`, but that method sits *above* `MUD_PREFIX` in step 10's file. Both `ensure` blocks in the new step 11 called a method that did not exist.
- **The tests did not catch it and could not have.** They exercise `Tools::Mcp.register` directly; nothing in the suite calls `Boukensha.repl`, which is where the `ensure` lives. The plain-REPL smoke check found it on the first run.
- Two bugs in one hand-applied delta, which is evidence for the question the plan itself raised: whether the remaining steps should be regenerated from step 11 rather than patched independently.

## Three more instances of an artifact being older than what is on disk

- **Step 11's `Gemfile.lock` still pinned `mud_manager 0.1.0`** — the version with no `fake_mud` and no binary. Under `bundle exec` the daemon spawn failed with bundler reporting a missing executable, which names the symptom and not the cause. Step 10 had the same stale pin; it was fixed earlier in the day by luck rather than by checking.
- **The installed `boukensha-0.11.0` gem carries the rc-parsing change but not the `--no-tui` restore** — built from the window between breaking the flag and fixing it. The global command runs the *installed* loader, so `boukensha --no-tui` is accepted and silently ignored.
- **Running `boukensha` from inside a step directory double-defines `Boukensha::VERSION`.** That step's `Gemfile` has `gemspec`; bundler evaluates the gemspec, which `require_relative`s its own `version.rb`; then the loader requires a *different* step's library on top. Only the constant collides, but the banner therefore reports whichever step loaded last — a version number that is not the code running.
- **Fourth, fifth and sixth instances this week.** The pattern is no longer a surprise, which makes it worth stating as a rule rather than an anecdote: **anything installed, locked, or built is a cache, and every one of them failed by reporting something other than staleness.**

## Porting step 11 to Python

- **The instructor's plan again assumed a starting state this repo does not have** — second time in one day. It specified `__version__` in `__init__.py` (ours is `VERSION` in `version.py`), wiring `tui=` into `__init__.py` (ours lives in `run.py`), Ruby step 11 at `0.11.1` (ours is `0.11.0`), `Repl` needing no visibility work (true of attributes, false of `_banner` and `_mud_status`), and `tool_count` as an attribute (it is a method). Diffing the assumptions before starting cost minutes; discovering them one at a time during implementation would have cost hours.
- **`_output` had to reimplement Ruby's `puts`.** Ruby leaves a trailing newline alone; Python's `print` adds a second. The plain `tui=False` REPL is the only fully deterministic gate this step has — a full-screen app is not diffable — and it is a gate only while it stays byte-identical to step 10's output. A one-line detail holding up the entire verification strategy.
- **A crash on quit, found by test timing rather than by use.** Textual keeps firing an interval while the app tears down, by which point the widgets it queries are gone. Individually every test passed; the full suite failed, because suite timing lands a tick inside the teardown window and interactive timing usually does not. **The bug was in the code the whole time and only the harness's different rhythm exposed it** — the inverse of a flaky test.
- **A name collision that predates the step.** `boukensha.repl` is both a submodule and a re-exported function, and `__init__.py` binds the function over the module, so `import boukensha.repl` returns a callable. Harmless until a test needs to patch the module.
- **Cancellation is a documented capability gap, not a port.** Ruby's Esc calls `Thread#raise(Interrupt)`, which lands wherever the turn thread is, including inside a blocking read. Python's nearest equivalent only fires when the thread next returns to bytecode, so it cannot cut short an in-flight HTTP call — it would take effect once the call returned, which is exactly when it stops mattering. Chose a cooperative `threading.Event` checked each iteration and wrote the gap down, rather than shipping something that resembles the Ruby behaviour and silently fails in the only case worth cancelling.
