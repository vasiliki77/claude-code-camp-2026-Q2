# 04-08-2026

Building the MCP layer for `mud_manager`, then reworking it to the instructor's design. Almost every problem was a *signal* problem — something that worked reporting that it didn't, or something broken reporting nothing at all.

## Three things that looked broken and weren't, and one that looked fine and wasn't

- **A stdio server is indistinguishable from a hang.** `mud-manager --mcp` at a shell prompt prints nothing and waits on stdin forever. That is exactly correct — it is a subprocess an agent spawns, not a program a human runs — but the observable behaviour of "working" and "frozen" is byte-identical.
- **The REPL banner reported the opposite of the truth.** The MCP path deliberately disables the in-process MUD tools, and the banner reads that flag, so it printed `mud: (not configured)` while 26 MUD tools sat registered and working. **A status line derived from one of two mutually exclusive routes will confidently describe the route that is switched off.**
- **A timeout error printed the wrong number.** `Session#read_until` interpolated its `timeout:` *argument* rather than the value it enforced, so every caller relying on the default got `after s`. That is the one number separating "too slow" from "waiting for the wrong thing", and its absence cost real diagnosis time before it was noticed as a bug rather than a formatting quirk.
- **The one that looked fine:** `BOUKENSHA_MCP=1 boukensha` printed a normal banner, booted normally, and silently ignored the variable entirely. No error, no warning. Diagnosed only because the banner said the wrong route — the misleading signal from two bullets up is what exposed the silent one.

## `~/.boukensharc`: step 09 built it, step 10 never received it

- **Running `boukensha` aborted with the rc file's own contents echoed back as if they were a path.** Step 09 had extended `~/.boukensharc` from a bare path to `KEY=value` lines; step 10's loader still did `File.read(rc).strip` and treated the whole multi-line file as one very long directory name. `File.expand_path` does not raise on that — it just yields a directory that cannot contain `lib/boukensha.rb`.
- **Nothing marked the capability as dropped rather than forgotten.** Each step folder is a standalone snapshot, so "step 10 no longer parses KEY=value" and "step 10 was written without thinking about it" are indistinguishable from the code. The instructor has a name for this class — a *floating artifact*: code a step built that the next step's rewrite did not carry forward.
- Carried the parser forward into step 10. **Steps 11 and 12 still float** — third time this same change has been noted as pending.

## "Which lib runs" and "which gem is installed" are still two questions

- **`BOUKENSHA_MCP=1` did nothing because the installed gem was `boukensha-0.9.0`.** It had step 09's rc parser — which is why the config directory resolved correctly and nothing looked wrong — but predated the MCP switch. So the global command ran step 09's *loader* while loading step 10's *lib*.
- **Third instance of this shape this week**, after the counted `..` paths and the built-but-never-installed `mud_manager`. Every time, the artifact on disk was newer than the artifact actually executing, and every time the failure named something else.

## `Session#login` had a third case nobody had met

- **tbaMUD answers a password three ways, not two.** Besides `Welcome` and `Reconnecting` it may say `You take over your own body, already in use!` — the linkdead take-over path. The login regex matched neither, so it waited the full timeout and failed.
- **It only became reachable once there were two ways to connect.** CircleMUD keeps a character in-world briefly after a disconnect, so running the daemon, exiting, and immediately starting the REPL reliably triggers it. The bug had existed all along with nothing to expose it.
- **First edit to `session.rb` since the gem was written.** Two lines, both about reporting: one pattern, one error message.

## Two Ruby behaviours that bind to the wrong thing without complaining

- **Splatting a trailing hash into `public_send` passes it positionally.** Ruby 3 separates positional and keyword arguments strictly, so `*[:method, {target: x}]` reaches a keyword-only method as a positional Hash and raises — for every one of the primitives that takes keywords. Caught before running, but only by reading rather than by testing.
- **A bare constant resolved up the lexical scope to a different class.** Inside `Boukensha::Tools::Mcp`, `Client` found `Boukensha::Client` — the LLM API client — rather than the MCP one, and the subsequent `.spawn` landed on `Kernel#spawn`. **Ruby resolves this silently to the wrong class instead of raising `NameError`**; the tests caught it, reading would not have.

## A failing check that was wrong about the code

- **An assertion counted logins by looking for the character name among received commands.** The fake MUD only records lines received *after* authentication, so the count was always zero. The code under test was correct; the check was measuring something that could not exist.
- Same lesson as the `or True` assertion earlier in the week, inverted: a check that cannot pass is at least loud, where a check that cannot fail is silent.

## Precedence that held on one path and inverted on the other

- **Forwarding config into a child process overrode inherited environment variables**, reversing the documented rule that env wins over config. It broke only on the MCP path — the in-process path still honoured the variable — so the two routes to the same tools would have disagreed about which credentials to use, with nothing reporting a conflict.

## Limits found and deliberately not fixed

- **Tool results are Strings all the way down.** The agent loop coerces every result with `to_s` before it reaches the context, so no MCP server can ever return an image or a resource to the model, however well the client handles it. Fixing that touches the context, the agent, and all five backends.
- **Every tool parameter is advertised as required**, regardless of intent, because the backend builds the required list from all parameter keys. Harmless against our own schemas, and a genuine defect against third-party ones.
- Both were left alone. They are pre-existing, they affect all tools rather than the MCP ones, and bundling them into this work would have made a refactor unreviewable.

## The plans disagreed with themselves, and with this repository

- **A plan's body and its inline replies recommended opposite things.** The written recommendation made the generated spec canonical; the inline answer made Ruby canonical. Another pair deferred multi-session while the reply required it. The replies are newer, so they win — but nothing in the document says so, and reading it top-to-bottom gives the wrong answer twice.
- **The instructor's follow-up plan assumed a starting state this repo does not have.** It expected two gems, a MUD-specific tool module and a bridge living in the daemon; here the gems were already merged and the bridge was already generic. Roughly a third of its migration was complete before it was read, and one step did not apply at all. **A plan is written against a snapshot; executing it means diffing the snapshot first.**
