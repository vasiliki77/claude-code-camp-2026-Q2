Running the steps rather than porting them. Three confusions, all about *which* thing I launched and *where* it looked for gems — none about agent code.

## I renamed a launcher because I misread the numbering

- **Renamed `bin/ruby/10_standard_tool_library` to `09_standard_tool_library`, `cd` line included.** It failed at once: `cd: .../ruby/09_standard_tool_library: No such file or directory`.
- **I "corrected" the wrong half of a real off-by-one.** `09_global_executable/README.md` is titled "Step 8" and calls its bundled lib "step 7's lib" — step *names* trail folder *numbers* throughout. So I read the tool library as "Step 9" and assumed the `10_` launcher had drifted.
- **Launchers are named after folders, not steps** (`08_the_repl_loop` → `ruby/08_the_repl_loop`). Folder `09_` is `09_global_executable`, so the name I wanted was taken. Folders `00`–`12` are contiguous and correct; only the README titles lag.
- **The launcher states its step name twice** — the filename, and the hardcoded `cd` path. Renaming one copy broke it silently: the same shape as yesterday's `..`-counting bugs.

## `bundle install` in the launcher

- **I was retyping `bundle install`, so it now lives in all 12 `bin/ruby/*`**, after the `cd` so it reads the right `Gemfile`:
  ```bash
  bundle check >/dev/null 2>&1 || bundle install
  ```
- `bundle check` exits non-zero when the lockfile is unsatisfied or absent, so an install happens only when something is genuinely missing. Output left visible — steps 10–12 fetch real gems and silence would read as a hang.
- **Noise I chose to live with:** `Bundler 4.0.10 is running, but your lockfile was generated with 2.5.19. Installing Bundler 2.5.19 and restarting using that version.` `bundle update --bundler` would silence it but rewrites lockfiles in 13 folders.

- **Bundler accused the author of deleting the gem:** *"locked to mud_manager (0.1.0) … can no longer be found in that source. That means the author … has removed it."*
- **It was never published.** `gem list -r -a mud_manager` returns nothing, the rubygems API 404s, search returns `[]`. It is an in-repo gem: `week0_explore/mud_manager/`, `0.1.0`, instructor-authored, no external dependencies.
- **`gem build` had run; `gem install` had not.** `mud_manager-0.1.0.gem` sat in the folder beside four `boukensha-*.gem` I had also built, and the artifacts made me read the job as done. **A built gem is a file; an installed gem is on the load path — only the second satisfies bundler.**

## `boukensha` vs `bin/ruby/<step>` — the one worth recording

- **I assumed these were two doors into the same room**, treating the global executable as "the same thing but convenient". That is why I could not predict which would work.

  | | `boukensha` | `./10_standard_tool_library` |
  |---|---|---|
  | Entry point | `Boukensha.repl` — interactive | `examples/example.rb`, then exits |
  | Which step | whatever `~/.boukensharc` says | always its own folder |
  | Gems | globally installed, **no bundler** | `bundle exec`, that step's lockfile |
  | Working directory | wherever I am standing | the step folder it `cd`s into |

- **Interactive vs scripted I had not noticed at all** — the launcher runs a fixed example and never waits for input, so there is no way to converse with step 10 through it.
- **They are not even running the same step.** My `~/.boukensharc` points `BOUKENSHA_PATH` at `09_global_executable`, whose bundled lib is step 08's — so `boukensha` gives me the REPL *without* the standard tool library.
- **The bundler difference caused the whole afternoon.** The launcher resolves from its step's lockfile; the global command has no Gemfile in the picture and uses global gems. Hence `mud_manager` needing installation, and hence the global command relying on my global gems agreeing with a step's lockfile.
- `BOUKENSHA_PATH=.../10_standard_tool_library boukensha` works now, would have failed an hour earlier, and **still fails for 11–12** — the two paths disagreeing about the same step.

### Taking from it

- **"Which lib runs" and "which gems are available" are independent questions I had fused into one.** `~/.boukensharc` answers the first; bundler answers the second, and the global executable never invokes it.
- **Every launcher-shaped thing here states a path or a name twice** — filename vs `cd` line, lockfile vs installed gems, `BOUKENSHA_DIR` vs where the config lives. Three of yesterday's bugs and two of today's are that shape.
